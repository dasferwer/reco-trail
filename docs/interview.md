# Как объяснить проект

«Я сделал сервис рекомендаций на FastAPI и PostgreSQL. В нём есть популярность,
подбор по жанрам и SVD-модель, которую я обучил на MovieLens. Сравнил их на будущем
временном отрезке по Recall@10 и NDCG@10. Выбор делал на validation, test оставил
для итоговой оценки.

Со стороны backend важно согласовать события и выдачу. Повтор не создаёт второй
лайк, позднее событие не отменяет более новое, а рекомендации используют одну
версию профиля и каталога. Это проверено конкурентными тестами, ошибкой внутри
транзакции и перезапуском API через SIGKILL».

## Решения

- **Baseline:** жанры уступили популярности, hybrid улучшил NDCG, collaborative
  дал лучший Recall. Дополнительная сложность имеет измеримый результат на этом тесте.
- **Общий временной split:** отдельный split пользователей может допустить обучение
  на событиях других людей из будущего относительно проверяемой выдачи.
- **Блокировка пользователя:** короткая транзакция упорядочивает один профиль,
  не блокируя записи других пользователей.
- **Версия в ключе кэша:** не нужно искать и удалять старые выдачи при каждом лайке;
  старые ключи становятся недоступны и вытесняются.
- **Холодный старт:** популярность без сигналов, жанры при предпочтениях; новые фильмы
  используют контент до появления факторов.
- **Отказ:** до commit изменения откатываются вместе; после commit повтор ключа
  возвращает сохранённый результат даже после перезапуска API.

Это самостоятельный учебный проект, а не коммерческий запуск. Маленький offline
test не доказывает рост CTR. Нет A/B-тестов и обучения глобальных факторов на
потоке API. Следующий этап — собирать показы вместе с реакциями, обучаться на
собственном потоке и проверять изменения на отложенном периоде. Большой каталог
потребует отдельного отбора кандидатов перед ранжированием.
